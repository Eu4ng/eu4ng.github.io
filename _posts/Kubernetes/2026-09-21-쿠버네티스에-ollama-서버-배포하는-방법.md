GitOps 저장소에 **Ollama** 매니페스트를 추가하고 push해 배포한 뒤, 클러스터 안의 GitHub Actions 러너에서 그 주소로 모델을 호출합니다. 모델은 초기화 컨테이너가 PVC에 한 번만 받아 두므로 파드가 다시 만들어져도 다시 받지 않고, 워크플로우마다 수 GB 모델을 내려받던 시간이 사라집니다.

1. 매니페스트 추가
2. 배포 확인
3. GitHub Actions에서 쓰기

## 사전 준비

> 이미 준비되어 있는 경우 건너뛰셔도 됩니다.
{: .prompt-info }

아래 환경을 기준으로 작성했습니다.

| 항목 | 버전 |
| :--- | :--- |
| Kubernetes | `v1.37` |
| Argo CD | `v3.5` |
| Ollama | `0.34.2` |
| 모델 | `gemma4:e4b (약 9GiB)` |
| 작성 기준일 | `2026-09-21` |

다음 항목이 준비되어 있어야 합니다.

- Argo CD와 기본 StorageClass가 있는 클러스터 ([쿠버네티스에 Argo CD 설치하고 GitOps로 서비스 추가하는 방법](/posts/36/) 참고)
- worker 노드에 모델 크기보다 넉넉한 메모리 (`gemma4:e4b`는 10Gi를 요청)와 디스크 40Gi
- 워크플로우에서 쓰려면 클러스터 안의 러너 ([쿠버네티스에 GitHub Actions Self-hosted Runner 등록하는 방법](/posts/35/) 참고)

## 1. 매니페스트 추가

GitOps 저장소의 `services/ollama/` 폴더에 PVC, Deployment, Service를 넣습니다. 폴더 이름을 따라 `ollama` 네임스페이스에 배포됩니다.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: ollama-models
  annotations:
    argocd.argoproj.io/sync-options: Prune=false   # 매니페스트를 지워도 받아 둔 모델은 남깁니다
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 40Gi          # gemma4:e4b 하나가 약 9GiB. 모델을 더 둘 생각이면 늘립니다.
```
{: file="services/ollama/pvc.yaml" }

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ollama
spec:
  replicas: 1                # 요청 한 건이 수 GB 를 씁니다. 늘리려면 메모리를 그만큼 잡습니다.
  strategy:
    type: Recreate           # PVC 가 ReadWriteOnce 라 새 파드와 겹쳐 뜨면 안 됩니다
  selector:
    matchLabels: { app: ollama }
  template:
    metadata:
      labels: { app: ollama }
    spec:
      # 모델은 여기서 한 번만 받아 PVC 에 둡니다. 이미 있으면 건너뜁니다.
      initContainers:
        - name: pull-model
          image: ollama/ollama:0.34.2
          command: ["/bin/sh", "-c"]
          args:
            - |
              set -e
              ollama serve &
              until ollama list >/dev/null 2>&1; do sleep 1; done
              ollama show "$MODEL" >/dev/null 2>&1 || ollama pull "$MODEL"
          env:
            - { name: MODEL, value: "gemma4:e4b" }
            - { name: OLLAMA_MODELS, value: /models }
            - { name: OLLAMA_HOST, value: "127.0.0.1:11434" }
          volumeMounts:
            - { name: models, mountPath: /models }
      containers:
        - name: ollama
          image: ollama/ollama:0.34.2
          ports: [{ containerPort: 11434 }]
          env:
            - { name: OLLAMA_MODELS, value: /models }
            - { name: OLLAMA_HOST, value: "0.0.0.0:11434" }
            - { name: OLLAMA_KEEP_ALIVE, value: "24h" }        # 모델을 메모리에 붙들어 둡니다 (첫 응답 지연 제거)
            - { name: OLLAMA_MAX_LOADED_MODELS, value: "1" }
          volumeMounts:
            - { name: models, mountPath: /models }
          readinessProbe:
            httpGet: { path: /api/tags, port: 11434 }
            initialDelaySeconds: 5
            periodSeconds: 10
          resources:
            requests: { cpu: "2", memory: 10Gi }   # 9GiB 모델이 상주하므로 실제 사용량만큼 요청합니다
            limits:   { cpu: "8", memory: 16Gi }
      volumes:
        - name: models
          persistentVolumeClaim: { claimName: ollama-models }
```
{: file="services/ollama/deployment.yaml" }

```yaml
apiVersion: v1
kind: Service
metadata:
  name: ollama
spec:
  selector: { app: ollama }
  ports:
    - { port: 11434, targetPort: 11434 }
```
{: file="services/ollama/service.yaml" }

모델을 바꿀 때는 초기화 컨테이너의 `MODEL` 값을 바꿉니다. 초기화 컨테이너는 `ollama pull`이 서버 없이는 동작하지 않으므로 서버를 잠시 띄웠다가 받고, 이미 받은 모델이면 바로 끝납니다. 메모리 요청량은 모델이 메모리에 상주하는 만큼 잡아야 노드 메모리가 부족할 때 퇴출 대상이 되지 않습니다.

```bash
# 커밋하고 push
git add services/ollama
git commit -m "feat: ollama 서비스 추가"
git push
```

- **확인:** 몇 분 안에 Argo CD 웹 UI에 `ollama` Application이 생기고 **Progressing**으로 표시

## 2. 배포 확인

control plane에서 파드가 초기화를 마치고 `Running`이 될 때까지 지켜봅니다. 이미지와 모델을 내려받는 시간이 필요하며, `gemma4:e4b`는 9.6GB라 11MB/s 회선에서 약 14분이 걸렸습니다.

```bash
# 파드 상태 지켜보기 (Init:0/1 -> PodInitializing -> Running)
kubectl get pods -n ollama -w

# 모델 다운로드 진행 상황
kubectl logs -n ollama deploy/ollama -c pull-model -f
```

파드가 `Running`이 되면 받아 둔 모델을 확인하고, 클러스터 안에서 API가 응답하는지 임시 파드로 호출해 봅니다.

```bash
# 받아 둔 모델 목록
kubectl exec -n ollama deploy/ollama -- ollama list

# 클러스터 안 주소로 API 호출
kubectl run curl --rm -it --restart=Never --image=curlimages/curl -- \
  http://ollama.ollama.svc.cluster.local:11434/api/tags
```

> PV가 worker 노드 한 대의 디스크에 만들어지므로 파드는 항상 그 노드에 뜹니다. 노드를 지우면 모델도 사라져 다음 파드가 다시 받습니다.
{: .prompt-warning }

- **확인:** `ollama list`에 `gemma4:e4b`, `/api/tags` 응답에 같은 모델 이름 표시. 파드를 지워도(`kubectl delete pod -n ollama --all`) 새 파드의 초기화 컨테이너가 모델을 다시 받지 않고 1초 만에 끝나 15초 안에 `Running`

## 3. GitHub Actions에서 쓰기

클러스터 안의 러너 파드는 클러스터 DNS를 그대로 쓰므로 `http://ollama.ollama.svc.cluster.local:11434`로 접근합니다. 주소를 저장소 변수에 넣어 두면 워크플로우 파일에 주소를 적지 않아도 됩니다.

```bash
# 저장소 변수에 Ollama 주소 저장
gh variable set OLLAMA_HOST --repo [OWNER]/[REPO] \
  --body http://ollama.ollama.svc.cluster.local:11434
```

{% raw %}
```yaml
name: Ollama Test

on:
  workflow_dispatch:

jobs:
  chat:
    runs-on: arc-linux-low
    steps:
      - name: 모델 목록 확인
        run: curl -fsS "$OLLAMA_HOST/api/tags"
        env:
          OLLAMA_HOST: ${{ vars.OLLAMA_HOST }}
      - name: 질문 하나 보내기
        run: |
          curl -fsS "$OLLAMA_HOST/api/chat" -d '{
            "model": "gemma4:e4b", "stream": false,
            "messages": [{"role": "user", "content": "쿠버네티스를 한 문장으로 설명해 줘"}]
          }'
        env:
          OLLAMA_HOST: ${{ vars.OLLAMA_HOST }}
```
{: file=".github/workflows/ollama-test.yml" }
{% endraw %}

- **확인:** **Actions** 탭에서 **Ollama Test** > **Run workflow**로 실행하면 첫 단계에 모델 목록, 둘째 단계에 모델의 답변이 출력. 응답 JSON의 `eval_count`를 `eval_duration`(나노초)으로 나누면 생성 속도가 나오며, CPU 8코어에서 약 7.5 토큰/초였음

## 마무리

Ollama 서버를 GitOps로 배포하고, 모델을 PVC에 한 번만 받아 두고 워크플로우가 클러스터 안 주소로 호출하는 구성을 완성했습니다. GPU가 없는 노드라 생성 속도는 CPU 8코어 기준 약 7.5 토큰/초에 그치지만, 워크플로우마다 반복하던 모델 다운로드는 없어졌고 모델 적재도 3초면 끝납니다. 실제로 논문 요약을 하위 모델로 검증하는 워크플로우에서 ollama 준비 단계가 2분 4초에서 1초로 줄었고, 산출물에는 `student_host`로 클러스터 안 주소가 기록되었습니다. 러너 파드와 같은 노드의 메모리를 나눠 쓰므로, 모델이 상주하는 만큼 러너에 줄 수 있는 메모리가 줄어드는 점은 감안해야 합니다.
