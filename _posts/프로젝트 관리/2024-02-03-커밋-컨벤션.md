커밋 메시지는 시간이 지나면 저마다 다른 형식으로 흐트러지고, 나중에 이력을 읽거나 변경 로그를 뽑을 때
쓸모가 없어집니다. AI 에이전트에게 커밋을 맡기면서부터는 문체까지 제각각이 되어 사람과 도구가 같은 기준을
보게 할 필요가 생겼습니다.

- **적용 범위:** 개인 저장소 전체, 사람이 쓰는 커밋과 AI 에이전트가 쓰는 커밋 모두
- **기준:** [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) 과
  [@commitlint/config-conventional](https://github.com/conventional-changelog/commitlint/tree/master/@commitlint/config-conventional)
  의 기본 규칙을 그대로 따르고, 표준이 정하지 않은 한국어 문체만 직접 정했습니다.

## 요약

> - 형식은 `type(scope): 제목` 이고 타입과 범위는 영어 소문자, 제목은 명사형으로 끝낸다
> - 제목에 마침표를 찍지 않고 100자를 넘기지 않는다
> - 본문에는 무엇을 바꿨는지가 아니라 왜 바꿨는지를 적는다
> - 규칙은 commitlint 와 husky 로 강제하고 사람의 기억에 맡기지 않는다
{: .prompt-tip }

## 1. 형식

- **규칙:** 헤더, 본문, 푸터 세 부분으로 쓰고 각 부분은 빈 줄로 나눈다. 본문과 푸터는 필요할 때만 쓴다.
- **이유:** Conventional Commits 가 정한 구조라서 commitlint, 변경 로그 생성기, 버전 자동화 도구가
  그대로 읽을 수 있습니다.

```text
<type>(<scope>): <제목>

<본문>

<푸터>
```

```text
# 좋은 예
fix(ci): auto-merge 워크플로우의 대상 브랜치를 main 으로 변경

master 브랜치를 main 으로 바꾼 뒤에도 워크플로우가 master 를 가리키고 있어
PR 이 자동으로 병합되지 않았다.

# 나쁜 예
Update workflow
```

## 2. 타입

`@commitlint/config-conventional` 이 허용하는 타입만 씁니다. 다른 타입을 쓰면 커밋이 거부됩니다.

| 타입 | 용도 |
| :--- | :--- |
| `feat` | 사용자에게 보이는 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서, 게시글, 주석만 변경 |
| `style` | 포매팅, 세미콜론, 공백처럼 동작에 영향이 없는 변경 |
| `refactor` | 기능 변화 없이 코드 구조 변경 |
| `perf` | 성능 개선 |
| `test` | 테스트 추가, 수정 |
| `build` | 빌드 시스템, 의존성 변경 |
| `ci` | CI 설정, 워크플로우 변경 |
| `chore` | 위에 해당하지 않는 잡일 |
| `revert` | 이전 커밋 되돌리기 |

- **규칙:** 한 커밋에 타입이 둘 이상 필요하면 커밋을 나눈다.
- **이유:** 타입 하나가 커밋 하나의 성격을 대표해야 이력에서 골라 읽을 수 있고, 변경 로그에서 `feat` 와
  `fix` 만 뽑아내는 일이 가능해집니다.

## 3. 범위

- **규칙:** 범위는 변경이 닿는 모듈이나 영역을 영어 소문자로 적고, 저장소 전체에 걸친 변경이면 생략한다.
- **이유:** 제목만 보고 어디가 바뀌었는지 알 수 있고, 한 저장소에서 같은 이름을 계속 쓰면 검색이 됩니다.

```text
# 좋은 예
fix(ci): ...
feat(runner): ...
docs(post): ...

# 나쁜 예
fix(CI): ...
fix(GitHub Actions 워크플로우): ...
```

## 4. 제목

- **규칙:** 제목은 한국어로 쓰고 `추가`, `수정`, `제거`, `분리`, `변경`, `작성` 처럼 명사형으로 끝낸다.
  `~한다`, `~합니다`, `~함` 으로 끝내지 않는다.
- **이유:** 영어 표준은 명령형(`add`, `fix`)을 요구하는데 한국어에서 이에 대응하는 짧은 꼴이 명사형입니다.
  `~한다` 는 문장이라 길어지고, 이력에 문장체와 명사형이 섞이면 목록으로 읽을 때 눈에 걸립니다.
- **규칙:** 마침표를 찍지 않고 100자를 넘기지 않는다. 72자 안에 들어오게 줄인다.
- **이유:** 마침표 금지와 100자 상한은 commitlint 기본 규칙이라 어기면 커밋이 거부됩니다. `git log --oneline`
  이나 GitHub 목록에서는 72자 근처부터 잘려 보입니다.
- **규칙:** 파일 이름이 아니라 결과가 드러나게 쓴다. 게시글 커밋은 글 제목을 큰따옴표로 감싼다.
- **이유:** 어떤 파일을 고쳤는지는 diff 가 알려 주고, 제목은 diff 를 열지 않아도 무엇이 달라졌는지
  알려 줘야 합니다.

```text
# 좋은 예
docs: "쿠버네티스에 Ollama 서버 배포하는 방법" 게시글 작성
fix: ARC 러너의 자원 상한이 작업 컨테이너에 적용되지 않는 문제 수정
chore: 불필요한 폴더 제거

# 나쁜 예
docs: 게시글 작성 규칙과 발행 전 검증 절차를 스킬 문서로 모은다
fix: 새 게시글 4개에 permalink를 부여해 내부 링크 오류를 없앤다.
docs: 2026-09-21-ollama.md 수정
```

## 5. 본문

- **규칙:** 제목만으로 이유가 드러나지 않을 때만 본문을 쓰고, 무엇을 바꿨는지가 아니라 왜 바꿨는지를 적는다.
  줄은 100자 안에서 끊는다.
- **이유:** 무엇이 바뀌었는지는 diff 에 있습니다. 시간이 지나 남는 질문은 "왜 이렇게 했지" 뿐이고 그 답은
  커밋 본문에만 남길 수 있습니다. 100자 상한은 commitlint 기본 규칙입니다.
- **규칙:** 본문은 평서문으로 쓰고 문체를 섞지 않는다.
- **이유:** 본문은 제목과 달리 문장이므로 명사형으로 끊으면 오히려 읽기 어렵습니다.

## 6. 푸터

- **규칙:** 호환성이 깨지는 변경은 타입 뒤에 `!` 를 붙이고 푸터에 `BREAKING CHANGE:` 로 무엇이 깨지는지 적는다.
- **이유:** 버전 자동화 도구가 이 표기를 보고 메이저 버전을 올립니다. `!` 만 붙이면 제목에서 눈에 띄고,
  푸터가 있어야 내용이 남습니다.
- **규칙:** 이슈를 닫는 커밋은 푸터에 `Closes #번호` 를 적는다.
- **이유:** GitHub 이 병합 시점에 이슈를 자동으로 닫고, 이슈에서 커밋으로 오갈 수 있습니다.
- **규칙:** 도구나 AI 에이전트를 밝히는 `Co-Authored-By`, `Generated-by` 같은 줄은 넣지 않는다.
- **이유:** 커밋의 책임은 커밋한 사람에게 있고, 이런 줄은 이력을 검색하거나 변경 로그를 만들 때 잡음이 됩니다.

```text
feat(api)!: 사용자 조회 응답의 날짜 형식을 ISO 8601 로 변경

BREAKING CHANGE: created_at 필드가 Unix 타임스탬프 대신 문자열을 반환한다.
Closes #42
```

## 적용 방법

로컬에서는 husky 의 `commit-msg` 훅으로 검사하고, 원격에서는 GitHub Actions 로 한 번 더 검사합니다.
둘 중 하나만 있으면 훅을 건너뛴 커밋이 그대로 올라갑니다.

```bash
# 로컬 검사 (저장소 루트에서 실행)
npm install --save-dev @commitlint/cli @commitlint/config-conventional husky
echo "module.exports = { extends: ['@commitlint/config-conventional'] };" > commitlint.config.js
npx husky init
echo 'npx --no -- commitlint --edit "$1"' > .husky/commit-msg
rm .husky/pre-commit
```

{% raw %}
```yaml
name: commitlint

on: [pull_request]

jobs:
  commitlint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: wagoid/commitlint-github-action@v6
```
{: file=".github/workflows/commitlint.yml" }
{% endraw %}

- **확인:** `git commit -m "bad message"` 가 `subject may not be empty`, `type may not be empty` 오류와
  함께 거부됩니다.

AI 에이전트가 쓰는 커밋에는 이 글의 규칙을 그대로 옮긴 [commit 스킬](https://github.com/eu4ng/agent-skills)
을 씁니다. 스킬을 설치해 두면 에이전트가 커밋할 때 저장소의 기존 이력을 먼저 읽고 같은 문체로 맞춥니다.

## 예외

- 영어로만 커밋하는 저장소(공개 오픈 소스, 협업 저장소)에서는 제목을 영어 명령형 소문자로 씁니다.
  타입, 범위, 형식 규칙은 같습니다.
- `main` 에 병합하는 PR 의 병합 커밋은 GitHub 이 만드는 기본 메시지를 그대로 둡니다.
