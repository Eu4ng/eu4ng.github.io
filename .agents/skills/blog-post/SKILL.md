# 블로그 게시글 작성

Chirpy 테마 기반 Jekyll 블로그다. 글을 쓰는 규칙과 발행 전 검증 절차를 이 문서 하나에 모았다.
`_drafts/` 의 템플릿은 뼈대만 담당하고, 규칙의 출처는 이 문서다.

## 1. 유형을 먼저 정한다

| 유형 | 대상 | 템플릿 |
| :--- | :--- | :--- |
| 방법 | 설치, 설정, 연동, 환경 구축처럼 독자가 순서대로 따라 하는 글 | `_drafts/template-how-to.md` |
| 컨벤션 | 명명 규칙, 커밋 규칙, 브랜치 전략, 스타일 가이드, 권장 설정처럼 "이렇게 한다" 를 정해 두는 글 | `_drafts/template-convention.md` |

두 유형에 맞지 않는 글(API 사용 방법, TIL, 회고 등)은 템플릿이 아직 없다. 아래 공통 규칙만 적용하고,
같은 유형을 또 쓸 것 같으면 새 템플릿을 제안한다.

템플릿을 복사해 시작하되 기존 게시글의 구조나 표기를 그대로 답습하지 않는다. 기존 글은 시기마다
섹션 이름과 표기가 달라 기준으로 삼기 어렵다. 더 나은 방식이 있으면 개선하고, 이 문서를 함께 고친다.

## 2. 파일 위치와 front matter

- 경로는 `_posts/카테고리/하위카테고리/YYYY-MM-DD-슬러그.md` 다. **폴더 이름이 곧 카테고리**이므로
  기존 폴더와 대소문자, 띄어쓰기를 똑같이 맞춘다.
- 슬러그는 제목을 소문자로 바꾸고 공백을 하이픈으로 바꾼다. 확장자 앞에 공백이 없어야 한다.
- front matter 에 `date`, `permalink`, `categories`, `last_modified_at`, `redirect_from` 을 적지 않는다.
  `permalink` 는 `scripts/add_permalinks.py` 가, 나머지는 `_plugins/` 가 채운다 (5번 참고).
- `title` 은 결과가 드러나게 쓴다. 방법 글은 "~하는 방법" 또는 "~하기", 컨벤션 글은 "~ 컨벤션",
  "~ 전략", "~ 권장 설정", "~ 스타일 가이드" 형태다.
- `description` 은 검색 결과와 글 목록에 노출될 한 문장이다. 글 제목 아래에 이미 표시되므로
  첫 문단에서 같은 말을 반복하지 않는다.
- `tags` 는 소문자와 하이픈만 쓴다 (`gitlab`, `ci-cd`, `unreal-engine`). 컨벤션 글에는 `convention` 을 붙인다.

## 3. 본문 구조와 문체

- **본문 제목은 H2 만 쓴다.** Chirpy 에서는 H2 와 H3 가 거의 같은 크기로 보여 섞어 쓰면 구분되지 않는다.
  더 나눠야 하면 항목을 쪼개거나 안내 문장, 목록, 표로 잇는다.
- 첫 문단은 제목 없이 쓴다. 단계가 네 개 이상이면 번호 목록으로 요약한다.
  공식 문서와 다르게 진행했다면 무엇이 다른지 여기서 한 문장으로 밝힌다.
- 단계와 규칙 항목은 `## 1. 제목` 형식이다. 번호가 중복되거나 건너뛰지 않았는지 마지막에 점검한다.
- 트러블슈팅 항목은 제목 대신 `<details markdown="1">` 접기 블록으로 쓴다. `summary` 에는 독자가
  검색할 오류 메시지의 핵심 구절을 `<code>` 로 적고, 오류 메시지가 없으면 증상을 한 줄로 적는다.
- 템플릿에서 "(선택)" 이 붙은 섹션은 쓸 내용이 없으면 통째로 지운다. 제목의 "(선택)" 글자도 지운다.
- 본문 문장은 합니다체, 목록 항목은 개조식으로 쓴다.
- 굵은 글씨는 UI 라벨과 핵심 용어의 첫 등장에만 쓴다. 제품 이름마다 굵게 하지 않는다.
- UI 경로는 `**설정** > **일반** > **고급**` 형식으로 쓴다.
- 파일 경로와 명령어, 설정 키는 인라인 코드로 쓴다.

### 코드 블록

- 펜스 언어: 실행 명령은 `bash`, 설정은 `yaml` 또는 `json`, 형식·예시는 `text`, C++ 는 `cpp`,
  그 외 `dockerfile`, `ini`.
- 파일 내용인 블록에는 바로 아래 줄에 파일 라벨을 붙인다. 중괄호 안쪽에 공백을 둔다.
  ```
  {: file="docker-compose.yml" }
  ```
- 명령 블록은 주석으로 단계를 구분하고, 한 블록에는 한 가지 목적의 명령만 담는다.
- 자리표시자는 `[UPPER_CASE]` 로 통일한다. 실제 토큰, 조직 이름, 내부 주소는 절대 쓰지 않는다.
- **본문에 이중 중괄호나 중괄호 퍼센트 표기가 들어가면 그 코드 블록을 Liquid `raw` 태그로 감싼다.**
  GitHub Actions 워크플로우나 Helm 차트를 실을 때 자주 걸린다. 감싸지 않으면 Jekyll 이 그 자리를
  치환해 버려 빌드가 깨지거나 내용이 사라진다.

### 프롬프트 블록

한 섹션에 두 개 이상 쓰지 않는다.

| 클래스 | 용도 |
| :--- | :--- |
| `prompt-info` | 선행 조건, 건너뛰어도 되는 경우, 관련 글 안내, 적용 범위와 출처 |
| `prompt-tip` | 더 편한 방법, 알아 두면 좋은 점, 컨벤션 글의 요약 섹션 |
| `prompt-warning` | 실수하기 쉬운 부분, 버전에 따라 달라지는 동작, 어기면 문제가 생기는 규칙 |
| `prompt-danger` | 데이터 손실, 보안, 비용, 라이선스 문제 |

### 이미지와 참고 자료

- 이미지는 `/assets/img/post/` 아래에 두고 대체 텍스트를 구체적으로 쓴다. 바로 아래 줄에 기울임 글씨로 캡션을 단다.
- 참고 자료는 `- [제목](URL)` 목록이다. 공식 문서와 표준 문서를 먼저, 블로그를 뒤에 둔다.
  제목에 세로선이 있으면 역슬래시로 이스케이프한다.
- 블로그 안의 다른 글은 `[글 제목](/posts/N/)` 로 링크한다. 번호는 대상 글의 `permalink` 값이며,
  아직 permalink 가 없는 새 글을 가리켜야 하면 5번을 먼저 실행해 번호를 확정한다.

## 4. 유형별 규칙

### 방법 글

**따라 하는 데 꼭 필요한 단계만 넣는다.** 선택 설정, 조건부 팁, 대안 소개, 배경 설명은 넣지 않는다.
빠르게 따라 하는 것이 목적이므로 사족은 그대로 방해가 된다. 각 항목이 "이게 없으면 따라 하다 막히는가"
를 통과하는지 초안 단계에서 거른다. 필수 여부가 애매하면 넣기 전에 실제로 필요한지 먼저 확인한다.

- 여러 환경(예: Windows 와 리눅스)에서 명령이 같다면 장비별로 반복하지 말고
  "한 번만 하는 일 → 양쪽에서 똑같이 하는 일" 순서로 배치해 코드 블록을 한 번만 싣는다.
- 사전 준비에는 필요한 패키지 설치 명령(`sudo apt install ...` 등)을 구체적으로 적는다.
- 각 단계 끝에 `- **확인:**` 으로 성공했을 때 화면이나 출력에 무엇이 보이는지 적는다.
- **마무리에는 이 글에서 완성한 설치·배포 결과만 적는다.** 이 결과를 저자가 실제로 어디에 어떻게
  활용했는지, 그로 인해 개인 프로젝트나 워크플로우의 어떤 지표가 얼마나 좋아졌는지 같은 개인적인
  사용기·성과는 적지 않는다. 방법 글은 설치·배포 절차를 설명하는 글이지 사용 후기가 아니다.

### 컨벤션 글

- 규칙 한 줄은 "~한다", "~하지 않는다" 로 끝나는 단정문이거나 개조식이다. "가급적", "되도록" 은 피한다.
- **모든 규칙에 이유를 붙인다.** 이유를 댈 수 없는 규칙은 넣지 않는다.
- 좋은 예와 나쁜 예를 짝지어 보여 준다. 예시는 실제로 쓸 법한 것으로 고른다.
- 다른 곳에서 가져온 규칙이면 출처를, 직접 정한 규칙이면 직접 정했다는 점을 밝힌다.
- 값이 여러 개인 규칙은 표로 정리한다. 한 칸에 여러 값을 콤마로 나열하지 말고 값 하나를 한 행으로 나눈다.

## 5. 설치·셋업 글은 스크립트 방식으로 쓴다

명령을 단계별로 나열하지 말고 `assets/scripts/<분야>/<이름>.sh` 스크립트 하나로 묶는다.
글은 "내려받기 → 실행 → 확인" 흐름으로 쓰고, 스크립트 전문은 `<details>` 접기 블록으로 함께 싣되
assets 파일과 내용을 **정확히 일치**시킨다.

기존 스크립트(`assets/scripts/kubernetes/install-headlamp.sh`)의 구조를 재사용한다.

- 맨 위에 무엇을 하는 스크립트이고 어디서 실행하는지 주석으로 적는다.
- `set -euo pipefail`
- `# ---------- 환경에 맞게 수정 ----------` 변수 블록을 맨 앞에 둔다.
- `log()` / `die()` 함수와 `trap ... ERR` 로 실패 지점을 알린다.
- `# ---------- 1. 사전 검사 ----------` 처럼 번호 붙은 섹션으로 나눈다.
- 재실행할 수 있게 만든다 (`helm upgrade --install`, `kubectl apply`).
- **토큰 같은 비밀 값은 인자나 파일로 받지 않고 실행 중 `read -rs` 로 입력받는다.**

## 6. 사실 확인

- 웹 UI 의 메뉴 경로, 탭 이름, 권한이 어느 탭에 있는지는 문서 요약을 근거로 단정하지 않는다.
  요약이 분류를 틀리게 옮기는 일이 실제로 있었다. 사용자가 화면을 보고 있으면 그 화면이 기준이고,
  확인하지 못한 부분은 확인하지 못했다고 밝힌다.
- 표에서 짝이 되는 용어는 표기를 맞춘다 ("개인 계정 / 조직" 이 아니라 "개인 계정 / 조직 계정").
  구분 기준은 독자가 화면에서 실제로 고르는 항목을 따른다.
- 성능·자원·보안처럼 "설정했다" 와 "실제로 적용된다" 가 갈릴 수 있는 주장은, 관측 가능한 검증 방법을
  먼저 정하고 사용자가 돌려 본 결과를 받은 뒤에 글에 쓴다. 소스나 CRD 에서 "필드가 전달된다" 를
  확인한 것만으로 "그 기능이 동작한다" 고 쓰지 않는다.
- 표시·가독성 문제는 테마 CSS 를 덮어쓰기보다 게시글 양식을 바꾸는 쪽으로 해결한다. 판단 기준은 가독성이다.

## 7. 발행 전 검증 (건너뛰지 않는다)

push 하기 전에 저장소 루트에서 아래를 순서대로 실행한다.

```bash
# 1. 새 글에 permalink 번호 부여 (날짜순으로 다음 번호를 매긴다)
python3 scripts/add_permalinks.py

# 2. 사이트 빌드
JEKYLL_ENV=production bundle exec jekyll b -d /tmp/_site

# 3. 링크 검사 (CI 와 같은 명령)
bundle exec htmlproofer /tmp/_site --disable-external \
  --ignore-urls "/^http:\/\/127.0.0.1/,/^http:\/\/0.0.0.0/,/^http:\/\/localhost/"
```

- htmlproofer 가 `HTML-Proofer finished successfully` 를 낼 때까지 push 하지 않는다.
  `pages-deploy.yml` 이 PR 에서 돌리는 것과 같은 검사이므로, 여기서 통과하면 CI 에서도 통과한다.
- 1번을 건너뛰면 새 글이 슬러그 주소로 생성되어 다른 글이 걸어 둔 `/posts/N/` 링크가 전부 깨진다.
  2026-09-21 에 게시글 4개가 이 상태로 push 되어 내부 링크 7건이 깨지고 CI 가 실패했다.
- 빌드 중 나오는 태그 관련 `Conflict` 경고는 이전부터 있던 것으로 빌드를 실패시키지 않는다.
- 글은 `develop` 브랜치에 커밋한다. `main` 은 `develop` 에서 PR 로만 갱신되고, 병합되면 배포된다.
